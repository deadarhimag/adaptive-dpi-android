# Доменная фильтрация [план]

Доменная фильтрация использует общую транспортную платформу Android и работает без root, внешнего VPN-сервера и аналитического движка DPI. Она принимает локальное решение по достоверному имени. На 1B проверяются поддерживаемые точки наблюдения и способы исполнения. На 1C выбирается архитектура. Если 1B подтверждает простую и безопасную DNS-фильтрацию, базовый исполнитель и работа с локальными правилами входят в 1D. Полнота контракта, измерения и независимая приёмка следуют в 1E–1G. Все механизмы ниже запланированы.

## Политика по умолчанию

По умолчанию включены категории рекламы, трекеров, аналитических сервисов, телеметрии, подтверждённых вредоносных и подтверждённых фишинговых ресурсов. Отчёты об ошибках разрешены. Дополнительные международные или региональные списки устанавливаются по выбору пользователя. Неизвестные и смешанные ресурсы разрешаются при недостаточной достоверности. Правило относится к подтверждённому назначению домена или специализированной ветки сервиса. Принадлежность компании сама по себе не служит основанием блокировать её домены.

Доступны глобальное отключение фильтра, настройки категорий, индивидуальные настройки приложений и пользовательские правила и исключения. Для достоверно известного приложения его настройка переопределяет глобальную; при неизвестном или неоднозначном UID применяется общая политика. Глобальное отключение фильтра отключает весь механизм. Отключение категории убирает её правила из общей базы, пользовательские правила действуют независимо от категорий.

## Сопоставление и приоритет

| Тип | Совпадение с `service.example` | Совпадение с `x.service.example` |
| --- | --- | --- |
| Блокировка точного домена | Да | Нет |
| Блокировка домена и его ветки | Да | Да |
| Блокировка только поддоменов | Нет | Да |
| Исключение для точного домена | Да | Нет |
| Исключение для ветки | Да | Да |

Для подтверждённого специализированного сервиса основной режим охватывает домен и все его поддомены. После проверки глобального выключателя и настройки приложения действующие правила рассматриваются по приоритету. Сначала пользовательские исключения приложения, затем глобальные пользовательские исключения, правила приложения, глобальные пользовательские правила и включённые категории общей базы. Любое подходящее пользовательское исключение разрешает запрос. В пределах одного уровня применяется правило с наибольшим числом меток в основании. При равной глубине приоритет имеют точное имя, затем только поддомены, затем вся ветка. Для конфликтов одной категории общая база должна пройти проверку до публикации. При неразрешённой неоднозначности общей классификации запрос разрешается. Настройка одного приложения не распространяется на другие приложения.

Сравнение проходит по границам DNS-меток после приведения регистра, обработки завершающей точки и нормализации IDN в сопоставимое ASCII/Punycode-представление. Некорректные имена не дают положительного совпадения. Точный профиль IDN, правила для недопустимых имён и версия Public Suffix List фиксируются в 1B–1C совместно для сборщика каталога и клиента. Блокирующие правила для публичных суффиксов и общих зон хостинга отклоняются при подготовке и проверке базы. Для известного общего сервиса проверяется риск блокировки пользователей соседних ресурсов, в том числе на общей платформе размещения.

## Источники имени и границы

Основной источник имени — DNS. В 1B исследуются CNAME-цепочки, видимые TLS/QUIC SNI и HTTP Host. Для возможного учёта CNAME требуются проверенная связь ответа с вопросом, доверенная цепочка и ограниченное время жизни. Сценарии должны исключать блокировку соседей на том же CDN. Внешний SNI при ECH и совпадение по общему серверному IP не устанавливают имя ресурса. Автоматических блокировок по IP или подсети нет.

| Условие | Граница фильтрации |
| --- | --- |
| DoH или DoT вне наблюдаемого DNS | Содержимое запроса не видно. Доступный открытый сигнал оценивается отдельно. Зашифрованный DNS принудительно не отключается. |
| ECH | Имя внутреннего назначения может быть скрыто. Имя фронта недостаточно для блокировки. ECH принудительно не отключается. |
| Кешированный DNS | Новый запрос может отсутствовать. Истёкшая или неоднозначная связь имени с адресом не служит основанием для блокировки. |
| Прямое подключение по IP | При отсутствии независимо подтверждённого доменного имени доменное правило не срабатывает. |
| Смешанный и общий ресурс | Общий адрес, цепочка к CDN и принадлежность компании не доказывают рекламное или вредоносное назначение. |

HTTPS MITM не применяется. Фильтрация не гарантирует блокировку всей рекламы, в том числе рекламы на том же домене, что и полезный контент.

## Независимость от DPI

Локальный отказ получает отдельную причину завершения с указанием локальной политики. Этот исход исключён из сигналов сетевого сбоя, деградации и DPI. После него не запускаются активная диагностика, генерация, подбор и подтверждение стратегии. При отключении или сбое аналитического движка фильтрация продолжает работать по локальным данным. Разрешённый поток идёт по [Fast Path](ARCHITECTURE.md#fast-path) при отсутствии применимого проверенного правила DPI. Тесты измеряют ноль запросов к анализу и проб после локальной блокировки, а независимый контроль передаёт разрешённый трафик в том же сеансе. [План тестов](TESTING.md#план-проверок-транспортной-платформы-и-фильтрации).

## Мировой каталог доменов

Каталог планируется в `domain-blocklists/` текущего репозитория. Окончательные форматы выбираются на 1B. Интерфейс локального загрузчика зависит от версионированного формата, подписи и метаданных, чтобы в будущем каталог можно было выделить без изменения механизма фильтрации. Предлагаемая структура пока служит планом.

| Путь относительно `domain-blocklists/` | Назначение |
| --- | --- |
| `lists/` | Человекочитаемые исходные списки, разделённые по назначению |
| `exceptions/` | Исключения общей базы и обоснования |
| `catalog/` | Записи о доменах и сервисах, источники и история классификации |
| `scripts/` | Сборка, проверка и подготовка публикации базы |
| `tests/` | Фикстуры классификации, наследования и обновления |
| `licenses/` | Лицензии, уведомления и условия распространения |
| `manifest.json` | Версия, формат, происхождение и данные проверки пакета |
| `README.md` | Форматы, назначение и порядок обновления |

Объекты исследования включают мировые компании, рекламные платформы, производителей устройств, аналитические SDK и сервисы телеметрии. Запись каталога хранит домен, тип правила, категорию, компанию, сервис, назначение, источник и исходную ревизию, лицензию, достоверность классификации, риск ложной блокировки, дату актуализации и исключения. Объединённый список проверяется по происхождению исходных записей, включая транзитивно импортированные источники. На 1B отдельно проверяются лицензии, условия преобразования, встраивания в APK и распространения обновлений. Лицензия MIT проекта не распространяется автоматически на данные третьих сторон. [Реестр зависимостей и лицензий](DEPENDENCIES_AND_LICENSES.md).

Начальные кандидаты для исследования — HaGeZi DNS Blocklists, AdGuard DNS Filter, OISD, EasyPrivacy, StevenBlack, другие международные и региональные специализированные списки, документация и подтверждённые сведения о сервисах компаний. Источники оцениваются по точности, назначению, доле ложных срабатываний, лицензии и проверяемости происхождения. Правила URL и косметические правила из веб-фильтров нельзя механически расширять до блокировки целого домена. Списки Zapret2 для обхода DPI сохраняют своё назначение и в базу фильтра не импортируются. [HaGeZi](https://github.com/hagezi/dns-blocklists) · [AdGuard](https://github.com/AdguardTeam/AdGuardSDNSFilter) · [OISD](https://oisd.nl/) · [EasyPrivacy](https://github.com/easylist/easylist) · [StevenBlack](https://github.com/StevenBlack/hosts).

## Локальное хранение и обновления

Начальная база входит в APK с соблюдением лицензий. Рабочая и резервная проверенная версии хранятся в приватном хранилище. Пользовательские правила и исключения хранятся отдельно и переживают обновление или откат общей базы. Индекс должен быть компактным. Кеш учитывает нормализованное имя, подтверждённое приложение или общую область и версию правил, включая изменения исключений. SQLite/Room, Reverse Domain Trie, компактные бинарные форматы и memory-mapped index сравниваются на одних данных по задержке, памяти, размеру, обновлению и восстановлению. Выбор основан на измерениях.

GitHub — публичный источник обновлений. Исходные списки остаются в Git в человекочитаемом формате. Подготовленная база версионируется и публикуется отдельно от APK. На 1B сравниваются GitHub Pages и отдельные релизы каталога в том же репозитории. Предусмотрен отдельный workflow обновления и проверки. Изменения формата или встроенных данных проходят применимые проверки совместимости приложения. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) · [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Обновление запускается вручную или автоматически. Периодичность по умолчанию — раз в сутки, пользователь может её изменить. Клиент проверяет подпись доверенным ключом, контрольные суммы, совместимость формата и защиту от неавторизованного отката до активации. Подготовка индекса проходит отдельно от рабочей версии, переключение атомарно. При локальном сбое допустим возврат к предыдущей проверенной версии без понижения отметки последней принятой версии для сетевых обновлений. Зеркала доставляют ту же подписанную базу с теми же правилами проверки. При отсутствии GitHub или годного обновления продолжает работать последняя корректная локальная база.

Внешняя сеть нужна только для доставки обновлений. Принятие решений, хранение и обработка каталога целиком локальны. История соединений, запросы приложения к доменам и пользовательские исключения не отправляются в GitHub или другие внешние сервисы. Транспорт и локальная фильтрация сохраняют работоспособность без источника обновлений. Выбор формата, канала публикации и схема управления ключами подлежат проверке в 1B–1C.
