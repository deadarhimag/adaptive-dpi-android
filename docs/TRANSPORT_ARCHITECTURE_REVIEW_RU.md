# Архитектурный аудит после этапа 2.4.6

Основной тракт проверен на `bc911daa01fc5894b49c71b4301ab0cf818a5540`, а пути чтения и остановки UDP повторно проверены после изменения `6b869fbb7808813cf798c5c5ddf0e962ee54ec54`. Уровень поддержки Android в сборке — minSdk 29, compileSdk и targetSdk 36. API 37 входит в матрицу проверки устройства. Результаты конкретных тестовых прогонов ведутся отдельно в [отчёте транспорта](TRANSPORT_VALIDATION_2.4.6_RU.md). Сквозной обмен через TUN подтверждает работу прямого тракта в тестовом окружении. Эффективность преобразований на сетях с DPI пока гипотеза.

## Граница транспортного тракта

1. Служба устанавливает TUN и передаёт его файловый дескриптор мосту HEV. HEV/lwIP создаёт локальные SOCKS5-запросы. Для TCP запрос содержит назначение, а для UDP адрес назначения передаётся в кадре. Релей проверяет локальный секрет и открывает внешний поток через `OutboundTransport`.
2. Внешний сокет принадлежит `OutboundTransport.SocketLease`. Android-политика проверяет физическую сеть, создаёт дескриптор чтением опции, вызывает `protect()` и затем `Network.bindSocket()`. После этого транспорт выполняет connect и активирует сокет. Примитивы отправки доступны через `TcpConnection.write`. Они учитывают байты и ошибки. Дескрипторы внешних сокетов в JNI сегодня не передаются.
3. Минимальная точка эксперимента находится в направлении приложение → внешний TCP между чтением в `HevLoopbackRelay.tcp()` и вызовом `TcpConnection.write()`. Изменение границ записи в Kotlin технически возможно с сохранением владельца сокета, счётчиков и штатного закрытия. В прямом режиме следует сохранить текущий цикл. Тест должен доказать, что частичные чтения, EOF и отмена сохраняют последовательность байтов и завершают буферизацию.
4. `TCP_NODELAY` регулирует алгоритм Нейгла. Границы записей в поток зависят от приложения, фактическая сегментация зависит от стека, состояния сокета, MTU и разгрузки интерфейса. Оценку сегментации делать только по захвату на контролируемой линии. Создание второго сокета для передачи частей повредит непрерывности потока.
5. JNI имеет смысл рассматривать после измерений и только для функции, которой действительно нужен FD. Публичный `ParcelFileDescriptor.fromSocket` на API 29+ дублирует FD. Удерживаемый дубликат меняет жизненный цикл сокета и способен мешать отмене, поэтому его нельзя хранить на весь сеанс. Текущий контракт Stop не переносится на JNI автоматически. Для пробного узкого вызова понадобятся явное владение, ограничение времени работы и регрессия Stop. Оснований переносить релей в C пока нет.

TCP-парсер к нему неприменим. При ECH даже доступный внешний ClientHello не показывает внутреннее имя. DoH скрывает DNS-сообщение внутри HTTPS, поэтому счётчик трафика к DNS-порту не заменяет наблюдение имени. По умолчанию диагностика не сохраняет адреса или имена. ## Атрибуция приложения

На TUN есть исходная пара адресов и портов и протокол. В потоке HEV → релей исходная локальная сторона приложения до релея не доходит. Локальный адрес и эфемерный порт SOCKS-клиента принадлежат HEV. В текущем режиме служба допускает один выбранный пакет через `addAllowedApplication`. Это область маршрутизации, не дополнительное доказательство UID конкретного потока. В рамках доступного кода моста подтверждена передача FD TUN и состояния, а отдельный callback кортежа или UID не обнаружен. Полный внутренний нативный тракт закреплённой версии не покрыт этой проверкой.

`ConnectivityManager.getConnectionOwnerUid()` доступен с API 29 для TCP/UDP. Активной VPN-службе нужны **исходные** local/remote endpoints, а отсутствие записи или прав даёт неизвестный результат либо исключение. После закрытия/повторного использования порта и при неоднозначном сопоставлении рассчитывать на гарантированную атрибуцию нельзя. Для режима нескольких приложений сначала проверить сопоставление по кортежу в контролируемом AVD. Для достоверной атрибуции на релейной стороне потребуется передать контекст из точки до преобразования, например ограниченный session-scoped callback или side channel со строгой корреляцией. Менять SOCKS5/HEV до доказательства потребности не требуется. [VPN Builder](https://developer.android.com/reference/android/net/VpnService.Builder#addAllowedApplication(java.lang.String)) · [getConnectionOwnerUid](https://developer.android.com/reference/android/net/ConnectivityManager#getConnectionOwnerUid(int,java.net.InetSocketAddress,java.net.InetSocketAddress)).
