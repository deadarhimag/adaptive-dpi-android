# Дорожная карта

Номер этапа - это номер работы, а не версия приложения. Версию APK (`versionName`, `versionCode`) задаёт сборка, и она с этапами не связана.

**Цель первой рабочей версии:** пользователь включает приложение на Pixel 7 в сети Билайн - и YouTube в Chrome открывается сам, без настроек. Остальные возможности добавляются после того, как эта цель достигнута и проверена на телефоне.

Правило против бесконечного исследования: каждый этап заканчивается проверкой на Pixel 7; новый изолированный компонент не начинается, пока предыдущий не работает в реальном тракте.

## Этап 5. Пользовательский продукт

Always-on VPN и автозапуск (`SUPPORTS_ALWAYS_ON = true`, изменение манифеста по п. 27 AGENTS.md); интерфейс из [ARCHITECTURE.md](ARCHITECTURE.md); объяснения простыми словами; измерение батареи за сутки; матрица AVD API 29/34/36/37; подготовка релиза и уведомлений о лицензиях.

**Распространение - только GitHub Releases.** Release-сборка подписывается отдельным ключом выпуска; ключ хранится в секретах GitHub, не в репозитории. Workflow выпуска запускается вручную по тегу и прикладывает к релизу APK, SHA-256 файла и список изменений из коммитов. Приложение само в сеть за обновлениями не ходит: в «О приложении» - ссылка на страницу релизов и версия. Лицензия проекта - MIT (решение пользователя, 24 ноября 2026); совместимость компонентов проверяется в 5.6 (п. 14 AGENTS.md). Публикация релиза - только с разрешения пользователя (п. 15).

#### 1.1 Квота релея до аутентификации - выполнено (CI зелёный, PR #4)

- **Было:** `permits.acquire()` до `listener.accept()`; 32 молчащих подключения постороннего приложения на loopback останавливали приём.

5. DNS: наблюдение ответов UDP/53 в релее для связи адресов и имён (уровень B ключа, `NameCache` - [ARCHITECTURE.md](ARCHITECTURE.md), Т3; DNS-клиент - задача 2.0a); мера `dns-answer` отвечает проверенными адресами; сравнение резолверов - по таблице «DNS» [ARCHITECTURE.md](ARCHITECTURE.md).
6. Синтез из профиля и публикация ревизии из `:analysis` через `RulePublisher`.

**Тесты:** JVM - `tls-record-split` на ClientHello из `SSLEngine`: сервер на `SSLEngine` завершает рукопожатие (тот же handshake-message); грамматика позиций - таблица случаев; неизвестное поле отклоняет меру. Стенд - пять вариантов проверки каждой операции ([TESTING.md](TESTING.md), «Проверка операций»).

**Не делать:** менять байты handshake-сообщения в живом трафике (инвариант 14); применять меру к ключу без факта (инвариант 12).

**Влияние:** горячий путь релея, DNS через релей; оба набора AVD.

### Этап 3. Полный анализ

Порядок: 3.4 → 3.8 → 3.1 → 3.2 → 3.3 → 3.5 → 3.9 → 3.7 → 3.6 (условная).

#### 3.1 Анализ вариантов

**Цель.** Найти не только механизм, но и точное правило DPI, чтобы мера переносилась на соседние ресурсы без нового подбора ([ENGINE.md](ENGINE.md), разделы 5, 14, 17, 23).

**Шаги.**
1. **Минимальная пара** - в `ProbePlanner`: блокируемый вариант (имя ресурса, подгонка по живому трафику) и проходящий (нейтральное имя на тот же адрес). Если проходящего нет - пара не строится, анализ вариантов не начинается (это «блок по адресу» или `unknown`).
2. **Признаки различия** - перечень полей `Variant`, которыми отличаются варианты пары; каждое поле с упорядоченным списком значений.
3. **Деление пополам** - параметрическая проба: промежуточный вариант меняет половину различающихся признаков; K повторов; по исходу отбрасывается половина. Нестабильная точка останавливает деление, правило получает область «только этот ключ».
4. **Уточнение имени**: суффикс какого уровня по Public Suffix List (Т11), учёт регистра (только пробы без П2), положение имени относительно первого сегмента и первой записи.
5. **Факт с областью «класс ключей»** - `scope = {kind: class, value: "suffix:googlevideo.com"}`.
6. **Проверка предсказанием** - для следующего ключа того же класса мера применяется со второго соединения (раздел 14); исход - свидетельство за или против факта; противоречие сужает область (раздел 17).
7. **Путь `unknown`** - раздел 23: протокол аномалии; ограниченная проверка - не больше одной меры на каждое свойство из параметрических моделей каталога; экспорт.

**Тесты:** стенд `sni-suffix` - вторая цель получает меру со второго соединения без полного подбора; `residual`; модель вне каталога (сценарий стенда с правилом, которого нет в `models.json`) - `unknown`, протокол, бюджет не превышен; JVM - число шагов деления ≤ ⌈log₂ N⌉ × K.

**Не делать:** перебирать имена или позиции подряд; расширять область факта без предсказания.

#### 3.2 Вопросы В5-В8 и операции с `TCP_INFO`

**Условие начала:** 1.6 показал, что `TCP_INFO` читается на Pixel 7.

**Шаги.**
1. `tcp-split-guaranteed` в `MeasureExecutor`: `setTcpNoDelay(true)`; запись части; опрос `SocketOps.notSentBytes` с шагом 1 мс, не дольше 50 мс; остаток. Не дождались - остаток и пометка «разрез не гарантирован» в `FlowRecord`.
2. `disorder`: `Os.setsockoptInt(fd, IPPROTO_IP, IP_TTL, ttl)` с TTL из факта; гарантированный разрез; восстановить исходный TTL (прочитать его до изменения `Os.getsockoptInt`); остаток.
3. Параметрический поиск TTL: значения 1-32, двоичный поиск при монотонном предикате раздела 20; факт с областью «адрес» или «/24 (IPv4), /64 (IPv6)».
4. В5 - одна TLS-запись в двух гарантированных сегментах, граница внутри имени; В6 - чтение контрольного объёма до обрыва с параметрическим поиском порога (значения 16 КБ - 1 МБ удвоением); В7 - генератор QUIC Initial с целевым SNI (обратная операция Т5); полный В8 - пробы через паузы 2, 4, 8 … 60 с до прохождения (раздел 21).
5. `pause` - только при установленном факте «DPI сбрасывает сборку по тайм-ауту».

**Тесты:** стенд с PCAP - два сегмента при гарантированном разрезе; disorder - первый сегмент с пониженным TTL не дошёл до сервера, повторная передача дошла; модели `sni-stream`, `sni-drop`, `volume`, `quic-block` различаются.

#### 3.3 Слежение за изменениями DPI

**Шаги.**

### Этап 4. Сеть и приложения

#### 4.6 Измерения для решений по лимитам

**Шаги.**
1. Сценарии на Pixel 7 через раннер (1.6a): Chrome - YouTube 10 минут, лента новостей 10 минут; мессенджер в фоне 1 час.
2. Снимать раз в 5 с: число активных сеансов HEV и релея (`OutboundStatistics`), потоки (`/proc/self/status`, `Threads`), открытые дескрипторы (`/proc/self/fd`), память (`Debug.getPss`), CPU процесса (`Process.getElapsedCpuTime`); для простоя - интервалы без данных по каждому соединению.

4. Отчёт - таблица в [TRANSPORT.md](TRANSPORT.md) с датой, сборкой и сценарием.

**Готово:** есть данные для решения Т7 и тайм-аута 4.1a.

#### 4.0 Модель конкурентности релея для всего трафика

**Шаги.** Выбор по Т7 и данным 4.6 с объяснением пользователю до начала (п. 16); перенос копирования на выбранную модель без изменения протокола с HEV и без ослабления тестов `HevLoopbackRelayTest`; пересчёт `sessionLimit` в `ExperimentalTransport` и лимитов [TRANSPORT.md](TRANSPORT.md). **Тест:** нагрузочный JVM - 500 одновременных соединений без `SESSION_LIMIT` и `WORKER_REJECTED`, число потоков не растёт с числом соединений (критерий Т7); AVD оба набора; Pixel 7 - батарея в пределах цели.

#### 4.0a IPv6 в тракте

**Шаги.** Адрес TUN IPv6 (уникальный локальный `fd00::/8`, один адрес), маршрут `::/0` (с исключениями 4.1b), DNS IPv6 сети; HEV уже поддерживает IPv6 - проверить конфигурацию `tunnel.ipv6`; релей - `ATYP 4` в CONNECT и FWD_UDP; `OutboundTransport` - IPv6-адреса; `checkDestination` - запрет частных и link-local IPv6. **Тесты:** JVM для `ATYP 4`; AVD с IPv6; Pixel 7 на мобильной сети (DNS64/NAT64 оператора) и Wi-Fi.

#### 4.1 Смена сети без остановки VPN

**Шаги.** В `watchPhysicalNetwork` вместо остановки сеанса - событие смены сети; `OutboundTransport.updateNetwork(policy)` с политикой новой сети; `setUnderlyingNetworks(arrayOf(new))`; новая эпоха в `:analysis`; потеря всех сетей - состояние ожидания (новые соединения отклоняются, VPN не выключается); события старого сеанса отбрасываются по ID; Stop приоритетнее. Изменение `VpnLifecycle` - перечислить влияние (общий код). **Тесты:** `VpnLifecycleTest` на новые переходы; Pixel 7 Wi-Fi ↔ LTE 10 раз без ручного перезапуска; пробы старой эпохи отменены (журнал рассуждения).

#### 4.1a Тайм-аут простоя TCP

**Шаги.** По данным 4.6 выбрать тайм-аут простоя для режима «весь трафик» (порядок часов) и согласовать с HEV `tcp-read-write-timeout`; значение и измерение - в [TRANSPORT.md](TRANSPORT.md). **Тест:** мессенджер в фоне час без лишних переподключений (журнал транспорта).

#### 4.1b Локальная сеть мимо TUN

**Шаги.** Чистая функция `routesExcluding(prefixes)` в `:vpn`: для API 29-32 - набор маршрутов, покрывающих `0.0.0.0/0` минус `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10`, `224/4` (и аналоги IPv6 `fc00::/7`, `fe80::/10`, `ff00::/8`); для API 33+ - `Builder.excludeRoute(IpPrefix)` под `SDK_INT`. **Тесты:** JVM - объединение маршрутов покрывает публичное пространство без частных диапазонов; Pixel 7 - трансляция на ТВ и принтер работают.

#### 4.2 Пересоздание TUN при смене DNS

**Шаги.** `onLinkPropertiesChanged` физической сети: если `getDnsServers()` изменились - повторный `Builder.establish()` с новыми DNS, передача нового дескриптора HEV без остановки сеанса (проверить, поддерживает ли мост HEV замену дескриптора; если нет - пересоздание HEV с сохранением релея, и это назвать). **Тест:** Pixel 7 - смена DNS Wi-Fi в настройках роутера или переключение сетей с разными DNS.

#### 4.3 Атрибуция UID

**4.3a Патч HEV** по Т6: правка в `scripts/prepare-hev.py` через `replace_at`; JVM-тест релея на разбор имени пользователя `s=<ip>:<port>`; старое имя `adaptive` без кортежа - UID неизвестен, соединение работает.
**4.3b UID в релее:** `UidResolver` в `:vpn` - `getConnectionOwnerUid` с протоколом и кортежем; UID → пакет через `PackageManager.getPackagesForUid`; результат в `FlowKey`; ошибка или `INVALID_UID` - «неизвестно», задачи с приоритетом «Обычный».
**Тест:** AVD - два тестовых приложения различаются в журнале.

#### 4.4 Режимы захвата

**Условие начала:** 4.0, 4.0a, 4.1a, 4.1b выполнены. **Шаги.** Настройка режима в `SharedPreferences`; по умолчанию `addDisallowedApplication(собственный пакет)` и пакеты из списка «вне VPN»; «выбранные приложения» - `addAllowedApplication` по списку; смена режима - пересоздание TUN. Изменение поведения по умолчанию - назвать пользователю. **Тесты:** AVD и Pixel 7 - обычные приложения работают без изменений; проблемные получают меру; само приложение не попадает в TUN.

#### 4.4a Приоритеты приложений

**Шаги.** Приоритет в карточке приложения; хранение - `SharedPreferences` (`appRules` резервной копии); ключ задачи получает наивысший приоритет из приложений с отказами по нему; «Не подбирать» - `FlowPolicy.measureFor(key, uid)` возвращает прямой путь для этого UID. **Тесты:** JVM - порядок слотов; Pixel 7.

#### 4.4b Списки и исключение из VPN

**Шаги.** «Не трогать ресурс» и «Всегда подбирать» - сопоставление по видимому имени и ключу пользователя, при ECH - по внешнему имени; «Всегда подбирать» - подбор с первого отказа; исключение приложения из VPN из карточки и из уведомления о проблеме - пересоздание TUN. **Тесты:** JVM сопоставления; Pixel 7.
