# План реализации

Каркас этапа 1, модульные тесты состояния VPN и workflow сборки debug APK уже подготовлены. Ревизия этапа закрепляет восстановление согласия, владение сеансом, остановку и отзыв. Результаты модульных тестов, сборки Android-тестов и исполнения на устройстве фиксируем раздельно.

После каждого этапа фиксируем изменённые файлы, проверенные сборки и сценарии, результаты и оставшиеся ограничения. Результаты симулятора, Linux-стенда, эмулятора и физических устройств сопровождаем сведениями о среде. Диагностика и правила установленного приложения остаются локальными. [Архитектура](ARCHITECTURE.md) · [RWSE](RWSE_DESIGN.md) · [Матрица испытаний](TESTING_STRATEGY.md) · [Технологии](TECH_STACK.md) · [Кандидаты и лицензии](DEPENDENCIES_AND_LICENSES.md)

## Порядок внедрения проверок

1. После утверждения плана добавить Kotlin-ядро и симулятор рядом с модулями каркаса. В GitHub Actions запускать модульные и симуляционные тесты и доступные интеграционные проверки по мере их появления. Для PR использовать быстрые представительные наборы, для расширенного прогона — тысячи сценариев с сохранением seed. Использовать JUnit и `kotlinx-coroutines-test` для виртуального времени.
2. Запустить минимальный pytest-стенд на Linux с синтетическим TCP/HTTP-сервером, DNS и TLS-фикстурами. Сначала проверить известный ответ и детерминированный отказ. Затем добавить сетевые пространства имён, профили `netem` и отдельный тестовый образ Docker. Проверить, что два параллельных прогона изолированы и что отменённый прогон освобождает ресурсы.
3. Подключить нативные проверки после выбора компонента. На Linux собирать переносимую часть C, на Android проверять жизненный цикл JNI и TUN для выбранных ABI. Контрольные сценарии из стенда использовать повторно, сохраняя отдельные результаты для каждой среды.
4. Добавить инструментальный smoke-набор для Android Emulator через ADB и Compose UI Test. Запуск расширенной матрицы вынести в отдельное задание с проверкой доступности виртуализации. Результаты с физических устройств оформлять по той же схеме, указывая режим сети и модель. [Уровни испытаний и GitHub Actions](TESTING_STRATEGY.md)
5. По отдельному решению подготовить статическую сводку GitHub Pages из обезличенных отчётов разработки. Отметить происхождение каждого набора данных. Сборка APK и работа на устройстве сохраняют независимость от публикации сводки. [Условия публикации](TESTING_STRATEGY.md#публичная-сводка-испытаний)

## Как измерять результат

- **Совместимость транспорта.** Для каждой ячейки фиксируем устройство, Android, ABI, тип сети, семейства IP на обеих сторонах, режим DNS и полученный ответ. Отдельно проверяем фрагментацию и MTU, время жизни UDP-ассоциаций и большие датаграммы. В неподдержанном сценарии тест подтверждает заявленное поведение маршрутизации.
- **Изоляция.** Длительная контрольная TCP-передача и активная UDP-ассоциация работают одновременно с пробами, отменой проб и публикацией правил. Проверяем целостность данных, отсутствие разрыва по вине этих операций и применение новой версии только к новым потокам. Смена или исчезновение физического маршрута — отдельный сценарий.
- **Энергия и производительность.** Сравниваем выключенный сервис, прямой локальный путь и режим диагностики при одинаковой нагрузке. Снимаем p50/p95 задержки, пропускную способность, память, загрузку CPU, фоновые байты, число проб и пробуждений. При отсутствии триггеров ожидаем ноль активных проб. Во время искусственного всплеска ошибок проверяем соблюдение заданных лимитов, слияние повторов и паузу перед повторной проверкой. Численные пороги сверх этого задаём после измерения прямого пути и до испытаний адаптации.
- **Достоверность.** Контрольный ресурс имеет стабильный ожидаемый ответ. Тестовая сеть воспроизводит проблемы с DNS, потерями, задержками, reset и captive portal, а тестовый HTTP-сервис — правовой или региональный отказ. Успех TLS фиксируется отдельно. Смена IP или сети в контрольной паре приводит к неопределённому результату. Неразличимые причины должны оставаться неопределёнными.
- **Воспроизводимость.** Для каждого прогона сохраняем ревизии движка, сценарий, конфигурацию и агрегаты без пользовательских данных. Для релизных утверждений указываем реально проверенные модели, версии Android и сетевые условия.

## Риски и вопросы до реализации

| Вопрос | Решение или критерий |
| --- | --- |
| Какой минимум Android и ABI поддерживать? | В каркасе установлен `minSdk 29`. Для нативного прототипа планируем `arm64-v8a` на физическом устройстве и `x86_64` там, где нужен эмулятор. Состав APK и заявленные ABI утверждаем после Android-тестов JNI и проверки канала распространения. |
| Доступны ли выбор на поток, защита исходящих сокетов и безопасный локальный интерфейс? | Проверить наличие точек интеграции на выбранных ревизиях. Если изменения достигают перезапуска процесса или широкой модификации стороннего ядра, сравнить стоимость адаптера и собственного обработчика до перехода к этапу 5. Прототип не публикуем с доступным другим приложениям незащищённым прокси. |
| Как вести себя на неподдерживаемом маршруте или после отказа? | До общего захвата выбрать явное поведение по семействам, локальным маршрутам, исключениям и lockdown. По умолчанию для захваченных стандартных потоков использовать прямой путь при наличии безопасного сокета. Проверить, что ошибки защиты сокета и потери сети не создают петлю или скрытую смену маршрута. |
| Чем верифицировать содержимое и когда запускать пробу? | Утвердить разрешённые ресурсы и версии контрактов, в том числе для динамического содержимого и UDP. Согласовать пределы перенаправлений, байтов, длительности, CPU и числа проб. Уточнить доступность диагностики в тарифицируемой сети и при энергосбережении. |
| Сколько сопоставимых пар достаточно? | Снять базовую вариативность на устройстве. Задать число повторов, минимальный выигрыш, допустимую долю отказов и отдельную подтверждающую серию. При непригодных парах или исчерпанном бюджете сохранять неопределённость результата. |
| Можно ли безопасно удержать одну сеть и запустить пробу с отдельной стратегией? | Проверить Android-путь с выбранным `Network`, настройками Private DNS, защитой сокетов и изолированным выбором преобразований. Сравнить условия между UDP и TCP, проверить атрибуцию за общим адресом CDN и при скрытом имени. До закрытия этих вопросов использовать только подтверждённые режимы проб. |
| Как надёжно привязать наблюдение к приложению и обнаружить деградацию? | Проверить сопоставление `UID`, `packageName` и профиля при разделяемом UID, изменении состава пакетов и ограниченной видимости. Снять базовые метрики живых потоков и подобрать пороги подтверждённого отказа и паузы. |
| Насколько надёжно распознаётся сеть между запусками? | Оценить доступные признаки без дополнительных разрешений. Если уверенного совпадения нет, использовать явно выбранный профиль или повторную проверку по триггеру. Утвердить сроки хранения, удаление данных из UI и набор диагностических сведений для экспорта. |
| Какие задания требуют специальных возможностей runner? | Для пространств имён и `netem` проверить права и модули ядра. Для ускоренного эмулятора проверить KVM и доступ к нему. Если среда не подходит, сохранять явную причину отсутствия результата и переносить этот набор на подготовленный Linux-host. [Аппаратное ускорение Android Emulator](https://developer.android.com/studio/run/emulator-acceleration) |
| Что касается распространения? | До выбора канала проверить условия распространения конкретного артефакта, Android SDK, нативные зависимости и видимость пакетов. Для Google Play требуется отдельная оценка применимости политики VpnService к локальной схеме, включая декларирование, раскрытие обработки данных и требование шифрования до конечной точки туннеля. Доступность публикации заранее не подтверждена. [Политика Google Play](https://support.google.com/googleplay/android-developer/answer/12564964) |
