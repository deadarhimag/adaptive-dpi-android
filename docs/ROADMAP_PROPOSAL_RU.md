# Предложение по дорожной карте после транспортной стабилизации

Это отдельное предложение к [исходному плану](IMPLEMENTATION_PLAN.md). Номера этапов относятся к работам. Версию APK задаёт сборка. Статус конкретного прогона проверяется по SHA, номеру попытки и результатам тестов. [Архитектурный аудит](TRANSPORT_ARCHITECTURE_REVIEW_RU.md) · [Проверка транспорта](TRANSPORT_VALIDATION_2.4.6_RU.md)

| Порядок | Работа | Критерий перехода |
| --- | --- | --- |
| 1 | Завершение транспорта 2.4.6 | Успех 21 базового и 7 расширенных сценариев Android AVD. Разобрать воспроизводимые ошибки Stop. Проверить счётчики освобождения, debug- и release-ABI. |

| 3 | Минимальный сквозной эксперимент | По явному согласию профиль одного тестового потока. Прямой профиль по умолчанию. Подтверждение точных байтов, Stop и фактической сегментации на контролируемой линии. Не распространять вывод на реальные сети. |

| 5 | Проверка на реальном устройстве | Pixel 7 Android 17, arm64. Сначала контроль прямого тракта, затем измерение при сравнимом состоянии сети и на ресурсах с известным ожидаемым содержимым. |

| 7 | Модель стратегий | Точечные политики по наблюдаемым признакам и уровню уверенности. Ограничить область действия и хранить контекст сети. |
| 8 | Адаптивный подбор | Измерять результат на добровольно выбранных ресурсах, ограничивать частоту и расход трафика. Отличать деградацию, отсутствие содержимого и неопределённый результат. |
| 9 | Пользовательский продукт | Ясное состояние VPN и подключения, опциональные пробы, установка с сохранением подписи, документация и проверки по матрице Android. |

## Статусы доказательств

- **Реализовано** — прямой Android VPN/TUN → HEV/lwIP → локальный релей → защищённые сокеты. В реализации есть диагностика задержки остановки.
- **Проверено JVM-тестами** — обработка релейных TCP/UDP-сценариев, отмена подготовленного TCP, короткий управляемый сценарий задержки релея и снимок его стека.
- **Проверено Android AVD** — в предыдущем CI отдельное приложение прошло обмен TCP/UDP/DNS/HTTPS, а второй Stop сорвал постановку комплекта как пройденного. На контрольной попытке 33.1 прошли 21 базовый и 7 расширенных сценариев. [Результаты](TRANSPORT_VALIDATION_2.4.6_RU.md#android-ci-331-контроль-после-исправления).
- **Проверено на реальном устройстве** — отчёты ранее подтверждали прямой обмен и отдельные сценарии на прежних сборках. Для текущей ревизии нужна отдельная проверка.
- **Реализовано локально** — компонент пробы ресурса и переключаемый из JVM-теста опыт с границами записи ClientHello. В опубликованной сборке 33.1 этих изменений нет.
- **Запланировано** — управляемый экран пробы, проверка сегментации по захвату, лабораторный фильтр, модель стратегий и адаптация.
- **Гипотеза** — локальный тракт без root и внешнего VPN-сервера сможет влиять на эффективность фильтрации конкретной реальной сети. Изменение границ записей, успешное TLS и зелёный CI по отдельности её не подтверждают.

## Контракт диагностической пробы

Компонент получает явно указанный пользователем или тестом ресурс, необязательное ожидаемое содержимое и политику дедлайнов. Он использует стандартный DNS и штатное доверие платформы, не зависит от состояния службы VPN. Стадия TLS включает верификацию имени и цепочки сертификатов. Перенаправление на другой хост следует считать отдельным результатом до появления явной политики. Буфер HTTP ограничен. Системные таймеры сокетов ограничивают блокирующие чтения. Отмена закрывает ресурсы I/O и возвращает отдельный итог, в том числе при гонке с завершением. Если системный DNS не может быть отменён немедленно, результат завершившегося позже запроса игнорируется в пределах выделенных воркеров.

Каждая стадия возвращает статус, длительность и безопасный классификатор. Категории — разрешение, ошибка сети, TLS, HTTP-статус, несовпадение содержимого, отмена, срок ожидания, неопределённый результат. HTTP-запрет фиксируется по наблюдаемому ответу без вывода о его источнике. Проверенные TLS и HTTP могут вернуть отсутствие подтверждения содержимого. В отчёт не идут тело, авторизация или cookies. Никакие результаты не уходят стороннему диагностическому сервису.

Локальная матрица включает DNS успех/отсутствие ответа, тайм-аут TCP, TLS с валидным тестовым CA и отдельный отказ верификации, HTTP 200/403/451, тело с нужным маркером или хешем, пустой/обрезанный ответ, запрет неограниченного редиректа, отмену до и после открытия сокета и разные дедлайны стадий. Для боевого компонента доверие TLS не подменяется. В тестах доверием к тестовому CA владеет изолированная конфигурация теста. Запуск без VPN, пакет с активным VPN и привязка сети при необходимости проверяются отдельно. Экран имеет смысл после подтверждения контракта.

## Контролируемый стенд

Топология Linux — клиент, промежуточный фильтр и HTTPS-фикстура в отдельных network namespaces на выделенной VM. Маршруты существуют только внутри лабораторного сегмента. Фикстура использует тестовый CA и синтетическое содержимое с жёстко заданным хешем. Клиент завершает тест успехом только при получении этого содержимого. Измеряются также время, результат TLS, решение фильтра, счётчики пакетов и PCAP с обеих сторон фильтра. Разгрузку сетевых интерфейсов следует отключать в лаборатории где доступно или сопоставлять наблюдения на двух точках с проверкой последовательностей и размера сегментов. Границы вызовов write в отчёт о сегментации не засчитываются.

| Фильтр | Профиль клиента | Условие эксперимента |
| --- | --- | --- |
| Выключен | Обычный | Контроль проходит, ожидаемое содержимое совпадает. |
| Включён | Обычный | Фильтр подтверждает решение о блокировке, содержимого нет. |
| Включён | Экспериментальный | Улучшение засчитывается, если фильтр действительно активен, захват подтверждает изменившуюся сегментацию, содержимое совпадает. |
| Выключен | Экспериментальный | Ожидаемое содержимое совпадает, потерь и дублей байтов нет. |
| Включён | Заведомо неэффективный | Содержимого нет, причина видна в журнале фильтра. |

Для простой блокировки IP/порта и отрицательного контроля достаточно правил nftables. Для модели с анализом данных можно передавать только синтетический трафик фильтру NFQUEUE на Linux. Очередь, время сценария и размер захвата ограничиваются. Сбой процесса фильтра должен завершать сценарий ошибкой. Полезно сравнить модель без сборки TCP-потока с моделью, анализирующей восстановленный поток. В первом случае успех может говорить об ограничении модели. Поведение реальных фильтров, QUIC и ECH этот результат не предсказывает. Прототип требует Linux со средствами создания namespaces, захвата и изолированной сетевой конфигурации. В Windows-окружении эти возможности не подтверждены. Обязательная привилегированная часть в Android CI не добавляется. [Механизм NFQUEUE](https://www.netfilter.org/projects/libnetfilter_queue/index.html) · [Существующая стратегия тестирования](TESTING_STRATEGY.md).

Для воспроизводимости назначить двум сегментам тестовые подсети `192.0.2.0/24` и `198.51.100.0/24`. Зафиксировать один адрес HTTPS-фикстуры, тестовое имя, SHA-256 ответа, версии ядра и инструментов. Каждый из пяти сценариев запускать на новом TCP-сеансе, сохраняя журнал решения фильтра и захват одной тестовой пары адресов. На фильтре отдельно сравнивать TCP sequence и размер полезной нагрузки до и после обработки, отмечать повторные передачи. В контрольном прогоне с IP/порт-фильтром ни одна граница записи не должна менять решение. Положительный тест лабораторной модели требует сравнения с фильтром, который умеет собирать весь начальный поток.

UDP/443 сохраняет прямой путь. В отдельном контролируемом тесте можно наблюдать режим без UDP, проверяя по захвату действительно ли данный клиент переключился на TCP и получил ожидаемое содержимое. Поведение зависит от клиента и конфигурации сервера. По умолчанию транспорт не блокирует UDP/443.

## Локальные прототипы после 33.1

Проба ресурса работает отдельно от службы VPN и выполняется один раз по запросу вызывающего кода. Она поддерживает собственные дедлайны DNS, TCP, TLS, HTTP и содержимого, штатное доверие Android и проверку имени TLS. В результатах остаются стадии, статусы, длительности и HTTP-код. Отмена coroutine закрывает сетевой сокет. Системное DNS-разрешение может пережить отмену, поэтому пул ограничен четырьмя рабочими потоками без очереди. Незашифрованный HTTP учитывает Android NetworkSecurityPolicy. Минимальная реализация проверяет первый разрешённый адрес, не следует редиректам, использует HTTP/1.x и ограничивает заголовок 16 КиБ, тело для проверки SHA-256 — 64 КиБ. Незнакомое кодирование содержимого даёт неопределённый результат. UI для пробы не добавлен. [Реализация](../vpn/src/main/kotlin/org/adaptivedpi/android/vpn/diagnostics/ResourceProbe.kt) · [Локальные тесты](../vpn/src/test/kotlin/org/adaptivedpi/android/vpn/diagnostics/ResourceProbeTest.kt).

Экспериментальная запись явно включается только тестовым конструктором релея. В обычном Android-конструкторе сохраняется прямой путь. Эксперимент хранит не более шести начальных байтов и перестраивает только границы записи. При EOF короткий префикс отправляется целиком, а Stop закрывает ресурсы штатным путём. JVM проверяет несколько чтений префикса, отсутствие повторной отправки после отказа записи, точное совпадение настоящего ClientHello из SSLEngine на принимающей стороне релея и Stop с неполным префиксом. Это доказательство для байтов потока. Захват реальных TCP-сегментов не выполнен. В текущем Windows-окружении нет доступного Linux network namespace / NFQUEUE или подтверждённого захвата на лабораторной линии. Перед включением в Android нужно проверить все пять режимов стенда с PCAP, получение ожидаемого содержимого и Stop. [Код опыта](../engine/src/main/kotlin/org/adaptivedpi/android/engine/ClientHelloSplitWriter.kt).
