# Тестирование и критерии приёмки

Главное правило: **каждый уровень проверки подтверждает только своё.** JVM-тест не подтверждает Android, эмулятор не подтверждает реальную сеть, стенд не подтверждает поведение DPI оператора, два вызова `write` не подтверждают два TCP-сегмента. В отчётах всегда указывается уровень. Подтверждённые результаты транспорта - в [TRANSPORT.md](TRANSPORT.md).

## Уровни

| Уровень | Что подтверждает | Чего не подтверждает | Где |
| --- | --- | --- | --- |
| JVM `:engine`, `:vpn`, `:analysis` | Логику, гонки, отмену, лимиты, разбор данных, решения движка на моделях DPI с виртуальным временем | Android API, ядро, реальную сеть | `./gradlew testDebugUnitTest :engine:test` |
| Нативные host-тесты **[план]** | Логику C, ASan/UBSan, поведение Linux-сокетов | Android-ядро, seccomp, JNI | Появятся вместе с `adaptive_ops.c` (задача 1.6) |
| Стенд целостности localhost **[есть]** | Работоспособность тестовых фикстур TCP/UDP/HTTPS | **Код приложения в нём не участвует** | `scripts/transport-host-lab.py`, `.github/workflows/transport-host.yml`, ручной запуск |
| DPI-стенд Linux **[план]** | Фактическую сегментацию по PCAP, работу операций и движка против управляемых моделей DPI | Поведение реального DPI оператора | Отдельный workflow |
| Android AVD | VpnService, жизненный цикл, TUN, HEV, JNI, протокол релея на Android | Реальное ядро устройства и сеть оператора | `.github/scripts/test-diagnostics-on-emulator.sh` (API 34) |
| Реальное устройство | Android 17 на Pixel 7, батарея, Doze, смена сети, реальное ядро | Другие устройства и сети | [PIXEL7_TESTING_RU.md](PIXEL7_TESTING_RU.md) |
| Реальная сеть | Эффективность обхода на сети оператора | Другие сети и будущие изменения DPI | Pixel 7, сеть Билайн |

Обязательные проверки зависят от того, что изменено (п. 30 AGENTS.md):

| Изменено | Обязательно |
| --- | --- |
| Код Kotlin, C, Gradle | `testDebugUnitTest :engine:test` и `assembleDebug`; для общего транспортного кода (`HevLoopbackRelay`, `OutboundTransport`, `AdaptiveVpnService`, мост HEV) - ещё базовый и расширенный наборы AVD. Новый или переименованный инструментальный тест вносится в списки `verify-android-test-results.py` (базовый набор) или `verify-extended-transport-results.py` (расширенный): они сверяют точные имена |
| Workflow и скрипты CI | `actionlint`, `bash -n`, синтаксис Python; прогон затронутого workflow |
| Только документация (`*.md`, `docs/**`, `LICENSE`) | Сборка не нужна; ссылки и согласованность документов между собой. Исключение - `docs/PIXEL7_TESTING_RU.md`: он входит в артефакт сборки |
| Выпуск | Задача 5.7 |

Результат привязывается к SHA. Непроведённая проверка называется в отчёте так и пишется - «не проверялось», а не «должно работать».

## Матрица CI

| Когда | Состав |
| --- | --- |
| Каждый push в `main` и каждый pull request, кроме правок только документации (`*.md`, `docs/**`, `LICENSE`; исключение - `docs/PIXEL7_TESTING_RU.md`, он входит в артефакт сборки) | JVM, lint, debug/androidTest/release APK, AVD API 34 базовый (24) и расширенный (7) наборы, проверка APK |
| Экспериментальные ветки | Черновой pull request в `main` ради Android CI без слияния |
| Вручную или по расписанию **[план]** | AVD API 29 (нижняя граница) и 36; API 37 - при наличии официального образа; нативные host-тесты с санитайзерами; фаззинг разборщиков |
| Лаборатория, вручную **[план]** | DPI-стенд Linux с PCAP |
| Перед каждым этапом | Pixel 7 по [PIXEL7_TESTING_RU.md](PIXEL7_TESTING_RU.md) |

Тест нельзя ослаблять или удалять ради зелёной сборки (п. 45 AGENTS.md). Повтор CI допускается один раз и только при подтверждённом инфраструктурном сбое.

PR из форков сейчас останавливаются до checkout (ключа подписи CI у них нет). Перед публичным выпуском - отдельный путь: тесты и сборка с временной debug-подписью без секретов (задача 5.7).

Обязательных проверок в настройках репозитория сейчас нет: для приватного репозитория на бесплатном тарифе правила ветки недоступны (API отвечает 403). Если они появятся (публичный репозиторий или платный тариф), фильтр `paths` оставит пропущенный workflow в состоянии «ожидает». Тогда обязательной делается короткая итоговая проверка, которая запускается всегда и сообщает, были ли пропущены тяжёлые задачи.

Правила синхронизации инструментальных тестов (найдены по падениям 24.11.2026):

- Удержание рабочего потока релея в хуке теста должно переживать `interrupt`: Stop прерывает рабочие потоки, и прерываемое ожидание отпускает поток раньше проверки.
- «Поток в `Socket.connect`» по стеку Java не доказывает, что SYN ушёл. Перед Stop тест ждёт состояние `SYN_SENT` (`02`) в `/proc/net/tcp{,6}`, прочитанное через `UiAutomation.executeShellCommand`, только для исходящего сокета релея: строка сопоставляется по номеру inode этого сокета (`/proc/self/fd` → `socket:[inode]`, поле `inode` в `/proc/net/tcp`), а не по удалённому порту - у сокета теста в TUN порт тот же. У каждого чтения shell свой срок 2 с: `withTimeout` блокирующее чтение канала не прерывает. Счётчик SYN на хосте остаётся независимой проверкой.
- Системный диалог ANR лаунчера («Quickstep isn't responding») на перегруженном эмуляторе перекрывает окно согласия VPN, и тест его не видит (запуск 45470164905, снимок `consent-screen.jpg`). Скрипт эмулятора выставляет `hide_error_dialogs 1` до установки APK. ANR самого приложения проверяется после прогона по журналу событий (`am_anr`, файл `app-anr.txt`), шаг падает при совпадении. Чтение журнала и проверка разделены: ненулевой код ADB - отдельная ошибка шага (`am-anr-adb.txt`); пакет сравнивается с третьим полем события `am_anr` (`User, pid, Package Name, Flags, reason`), а не с любой частью строки. Настройка действует только на одноразовом AVD CI.

## DPI-стенд Linux [план]

Топология - три сетевых пространства имён на одном Linux-хосте или раннере: **клиент** (JVM-тракт `:engine` или нативные тесты), **фильтр** (модель DPI), **сервер** (HTTPS-фикстура с тестовым CA и синтетическим содержимым с известным SHA-256). Соединения - veth-пары в подсетях `192.0.2.0/24` и `198.51.100.0/24`.

- Фильтр: nftables для правил уровня адреса и порта; NFQUEUE с обработчиком на Python для правил по содержимому.
- Захват: `tcpdump` на обеих сторонах фильтра; разгрузку сегментации (TSO/GSO) на veth отключать, иначе захват покажет склеенные сегменты.
- Отчёт: решение фильтра, PCAP, разбор сегментов и повторных передач, получено ли контрольное содержимое.
- Сбой процесса фильтра завершает сценарий ошибкой.
- Стенд не требуется для сборки APK и не меняет основной Android CI.

### Каталог моделей DPI

Одно декларативное описание модели используется и стендом, и JVM-моделями предсказания в `:analysis` ([ENGINE.md](ENGINE.md), раздел 22), чтобы они проверяли одно и то же. Каждая модель задаётся тремя полями: **уровень разбора** (сырые байты пакета, один TCP-сегмент, одна TLS-запись, собранный поток), **условие** и **действие** (RST клиенту, отбрасывание, заглушка). Шум задаётся отдельным параметром p для любой модели. Таблица ниже - краткие описания; точные значения трёх полей фиксируются в файле описания моделей вместе с реализацией стенда.

| Модель | Поведение |
| --- | --- |
| `pass` | Ничего не делает (контроль) |
| `ip-block` | Блок по адресу назначения |
| `dns-spoof` | Подмена ответа DNS для имени |
| `sni-first-packet` | Уровень: один TCP-сегмент, поиск строки имени в сырых байтах. Условие: имя целиком в первом сегменте с данными. Действие: RST |
| `sni-first-record` | Уровень: одна TLS-запись (сегменты собирает, записи - нет), разбор SNI. Условие: имя в первой записи. Действие: RST |
| `sni-stream` | Уровень: собранный поток и записи. Условие: имя в ClientHello. Действие: RST |
| `sni-suffix` | Как выше, но по суффиксу домена и без учёта регистра |
| `sni-drop` | Вместо RST молча отбрасывает |
| `residual` | После срабатывания блокирует пару клиент - адрес на T секунд |
| `volume` | Останавливает передачу после N КБ ответа |
| `throttle` | Уровень: собранный поток. Условие: имя в ClientHello. Действие: задержка пакетов ответа до заданной скорости R КБ/с, без сброса |
| `quic-block` | Отбрасывает UDP/443 для имени |
| `http-redirect` | Отвечает на HTTP-запрос редиректом на заглушку |
| `inject-tls` | Отвечает на ClientHello заглушкой с чужим сертификатом |
| `server-region` | Без DPI; сервер отвечает 451 или отказом по региону |
| шум p | Параметр любой модели: срабатывание с вероятностью p |
| `loss` | Без DPI, но с потерями пакетов (netem) |

### Схема каталога моделей [план]

Файл `analysis/src/main/resources/catalog/models.json` - единственный источник моделей для `:analysis` и стенда. Интерпретатор один на обоих сторонах: Kotlin `MechanismModel.predict(v)` и Python-обработчик стенда исполняют одни и те же поля; тест сверяет их предсказания на общем наборе вариантов.

```json
{
  "schema": 1,
  "models": [
    {
      "id": "sni-first-record",
      "level": "record",
      "match": { "on": "sni", "where": "first-record", "name": "exact-ci" },
      "action": "rst",
      "params": {}
    },
    {
      "id": "residual",
      "level": "address",
      "match": { "on": "after-trigger", "seconds": "param:t" },
      "action": "drop",
      "params": { "t": [10, 30, 60, 120] }
    }
  ]
}
```

| Поле | Значения |
| --- | --- |
| `level` | `packet` (один TCP-сегмент, сырые байты), `record` (одна TLS-запись, сегменты собраны), `stream` (поток и записи собраны), `address`, `dns`, `udp`, `http`, `server`, `network` |
| `match.on` | `none`, `address`, `sni`, `sni-suffix`, `dns-name`, `quic-sni`, `http-host`, `after-trigger`, `volume` |
| `match.where` | `first-segment`, `first-record`, `any` |
| `match.name` | `exact`, `exact-ci` (без учёта регистра), `suffix:<уровень>` |
| `action` | `pass`, `rst`, `drop`, `stub-http`, `stub-tls` (чужой сертификат), `dns-spoof`, `stop-after-bytes`, `reply-451` |
| `params` | Имя → список допустимых значений; параметрические пробы выбирают значение из этого списка |
| Шум | Не поле модели: задаётся сценарием стенда и `ModelProbePort` (`p`) |

`unknown` - не модель и в файл не входит: это исход диагностики «все модели исключены» ([ENGINE.md](ENGINE.md), раздел 28). У параметра модели может быть поле `monotone: true` с обоснованием - только для таких параметров допустим двоичный поиск. Новая модель добавляется только вместе с тестом стенда.

### Критерии приёмки движка анализа

Это критерии того, что движок действительно анализирует, а не перебирает.

| Сценарий | Ожидаемое |
| --- | --- |
| Модель `pass` | Ни одной пробы, ни одной меры |
| `server-region` | Диагноз «ограничение на стороне сервера»; проб после диагноза нет; мера не применяется |
| `loss` | Диагноз «общая проблема сети», правило DPI **не** найдено, меры не применяются |
| `ip-block`, у ресурса есть другой рабочий адрес | Диагноз «блок по адресу»; мера «DNS» с рабочим адресом; ресурс доступен |
| `ip-block`, рабочих адресов нет | Диагноз «блок по адресу» не больше чем за 2 × N различающих проб; `NotLocal`; объяснение пользователю |
| `dns-spoof` | Диагноз «подмена DNS» (В1), мера - собственный резолв |
| `sni-first-packet` | Найдено правило «первый сегмент, без сборки»; синтезирована мера уровня записей или сегмента; содержимое получено |
| `sni-first-record` | Найдено «записи не собирает»; мера - разбиение на TLS-записи |
| `sni-stream` | Этап 2 (без В5): «неразличимы» с `sni-first-packet` или «не решено». Этап 3: найдено «собирает поток»; меры уровней записей и сегментов **отвергнуты**; переход к TTL-уровню или `Unsolved` |
| `sni-suffix` | Правило содержит суффикс; предсказание для другого имени с тем же суффиксом подтверждается без нового поиска |
| `residual` | Обнаружено наказание; пробы одного адреса выполнены последовательно с паузой; результаты не испорчены |
| Любая модель с шумом p ≥ 0,3 | Факт помечен «нестабильный», мера из него не выводится |
| Смена модели во время работы (`sni-first-record` → `sni-stream`) | Датчик обнаруживает деградацию; перепроверяется факт меры; новая мера выводится; изменение записано в журнал |
| Отрицательный контроль во всех сценариях | Заведомо неподходящая мера не даёт успеха |
| Две разные цели с одним правилом (`sni-suffix`) | Вторая цель получает предсказанную меру со второго соединения (после первого отказа), без полного подбора |
| `inject-tls` | Пассивный датчик отмечает «клиент бросил соединение после ответа»; П2-проба ставит диагноз «подмена ответа на пути»; сертификат не принят |
| `volume` | Признак «остановка приёма» переводит ключ в `Suspect`, хотя принято больше 4 КБ |
| `throttle` | Признак «низкая скорость» записывается как телеметрия; на стенде определяются исходы В9, объём пробы, повторы и «недостаточно данных»; проверяются ложные срабатывания на медленном сервере, потерях и коротком ответе |
| Исключение в `:analysis` | Новые соединения идут прямым путём, релей работает |
| Сброс для эндпоинта приложения A | У приложения A ключ идёт прямым путём, у приложения B на том же ключе мера остаётся; повторный синтез для A не выдаёт отклонённую меру |
| Мера повышает отказы другого ключа приложения | Автооткат для пары «приложение - ключ», запись в журнале |
| Сеть с авторизацией (`CAPTIVE_PORTAL`) или без интернета | Ни одной пробы, ключи не в `Suspect` |
| `ip-block`, приложение со своим DoH | Мера «перенаправление»; ресурс доступен; сертификат подлинный |
| Повторный импорт того же файла | 0 добавлено; отчёт «объединено» |
| Импорт факта, противоречащего локальному | Локальный факт сохраняется, импортированный - конкурирующая гипотеза |
| Приложение с 10 эндпоинтами, блок у 2 | Меру получают только 2 ключа; остальные 8 без операций |
| Каждая модель каталога | Карточка ресурса показывает уровень «Доказано», «Подтверждено мерой» или правильный предел («недостаточно данных», «мера помогла, механизм не установлен», «транспорт доступен, содержимое не проверено») с экспериментами-свидетельствами; для `server-region` - «не DPI», без мер |
| Модель, против которой меры нет в каталоге | Состояние `Unsolved`; повторы по расписанию; бюджет не превышен |
| Операция недоступна на устройстве (эмулируется отказом нативной функции) | Соединение продолжается прямым путём; операция исключается из синтеза |
| Подтверждение | Мера подтверждена только при выполнении всех условий раздела 15 `ENGINE.md` |
| Неразличимые модели с общей мерой | Результат «мера помогла, механизм не установлен», без заявления о механизме |
| Недостаточно данных (шум, бюджет) | «Недостаточно данных» с оставшимися гипотезами, мера не публикуется |
| Легитимный междоменный 302/307 с успешным содержимым | Не отказ, не заглушка; проб нет |
| HTTP 451 без явного ответа о регионе | «Отказ сервера», без вывода о регионе и DPI |
| Разные завершения TLS 1.3 с одинаковым внешним типом записи | Пассивный датчик не делает вывода о внутреннем типе записи и причине закрытия |
| Локальный запрет незашифрованного HTTP | Статус `CLEARTEXT_BLOCKED`, сокет не открыт, движок не учитывает его как сетевой сигнал |
| Живые соединения на адресе отрицательного контроля | Контроль отложен или не проведён с записью предела; параллельная передача на общем адресе не нарушена |

**Проверка, что это анализ, а не перебор.** В каждом сценарии журнал рассуждения проверяется автоматически по типу каждой пробы ([ENGINE.md](ENGINE.md), раздел 22): различающая - не меньше двух живых гипотез с разными предсказаниями; параметрическая - не меньше двух значений параметра с разными предсказаниями; подтверждающая - одна живая гипотеза и не больше 2 × N проб на меру. Граница ⌈log₂ H⌉ × K различающих проб (H - живые гипотезы к началу диагноза, K - повторы при шуме) проверяется только в сценариях, где каждая проба по построению делит гипотезы пополам; в остальных проверяются бюджет и завершение с `Unsolved` или «неразличимы». Обязательные сценарии: пересекающиеся предсказания (`{PASS}` и `{PASS, RESET}`); исключение всех моделей (неизвестный механизм); два совпадения из трёх при K = 3; пробы, исключающие по одной гипотезе за шаг. N и K - из профиля качества ([ENGINE.md](ENGINE.md), раздел 21).

**Независимая проверка.** Стенд и `ModelProbePort` берут поведение из одного каталога, поэтому их согласие не доказывает диагноз: ошибку автора каталога оба повторят одинаково. Поэтому есть отдельный небольшой набор `analysis/src/test/resources/expected/` (`ExpectedVerdictTest`): входы с ожидаемым ответом, назначенным вручную без вызова `predict()`. В нём обязательны: две разные причины с одинаковым наблюдением (ожидаемый результат - предел вывода, а не одна причина), отказ контрольной точки, скрытая от движка смена условий, рабочий транспорт при ошибке сервиса, отказ сервера вместе с сетевыми потерями. На стенде ожидаемое содержимое и событие фильтра сверяются независимо от решения анализатора. Намеренное изменение предположения в каталоге должно ронять хотя бы одну независимую проверку. Тест падает, если движок выполнил пробу вне условий её типа. Приёмка анализатора по записанным данным и приёмка реальных эффектов - раздельные.

**Воспроизведение.** Протоколы, записанные на реальном телефоне ([ENGINE.md](ENGINE.md), раздел 24), хранятся как тестовые данные; JVM-тест подаёт их в движок и сравнивает диагноз и число проб. Изменение движка, ухудшившее диагноз на записанных данных, - регрессия.

Дополнительно для каждого сценария: число проб не превышает бюджета; действующие соединения не прерываются из-за проб; поздние результаты после смены эпохи не публикуются.

### Тестовая инфраструктура `:analysis` [план]

| Что | Назначение |
| --- | --- |
| `FakeClock` (реализует `Clock`) | Виртуальное время: старение очереди, бюджеты за час, паузы наказания проверяются без ожидания |
| `ModelProbePort` (реализует `ProbePort`) | Отвечает на пробу по `MechanismModel` из каталога, с шумом p от генератора с фиксированным зерном (только в тестах) |
| `catalog/models.json` | Каталог моделей: один файл для JVM-тестов и стенда |
| `LifecycleTransitionTest` | Все пары «состояние - событие» раздела 13 [ENGINE.md](ENGINE.md) против таблицы |
| `NoEnumerationTest` | Проверка журнала рассуждения по типам проб (выше) для каждой модели каталога |
| `ReplayTest` | Подаёт записанные протоколы из `analysis/src/test/resources/replay/` и сравнивает диагноз и число проб |
| `BackupCodecTest` | Повторный импорт, противоречащий факт, неизвестная операция, файл новее схемы |

## Проверка операций

Каждая операция из [OPERATIONS.md](OPERATIONS.md) проверяется в пяти вариантах:

| Фильтр | Операция | Ожидаемое |
| --- | --- | --- |
| Выключен | Нет | Содержимое получено |
| Включён | Нет | Содержимого нет, фильтр зафиксировал срабатывание |
| Включён | Подходящая | Содержимое получено; PCAP подтверждает изменённую форму |
| Выключен | Подходящая | Содержимое получено без потерь и дублей байтов |
| Включён | Заведомо неподходящая | Содержимого нет |

Для операций, меняющих байты потока (разбиение на TLS-записи), критерий целостности - сервер получил тот же handshake-message, а не те же байты.

## Разборщики недоверенных данных

`ClientHelloInspector`, будущие разборщики QUIC Initial, HTTP-ответа и DNS, а также разбор кадров SOCKS5/FWD_UDP в релее получают данные от любых приложений устройства. Для них обязательны property-тесты на случайных и повреждённых данных до предельного размера: нет исключений наружу, нет выхода за пределы буфера, время разбора линейно от размера.

## Стенд целостности localhost

`scripts/transport-host-lab.py` проверяет TCP, UDP и HTTPS фикстур между собой и пишет JSON-отчёт. Код приложения в нём не участвует; это проверка тестовой инфраструктуры.

```text
python -B scripts/transport-host-lab.py --certificate <cert.pem> --key <key.pem> --report <отчёт.json>
```

Сертификат - краткоживущий, для `localhost`, во временном каталоге; ключ удаляется после прогона.

## Автоматизированное тестирование

Цель: всё, что не требует человека, проверяется без человека - агентом (Codex) локально или GitHub Actions. Человек нужен только для решений и для того, чего автоматизация не может: реальная сеть оператора без подключения телефона к компьютеру.

### Что выполняет агент локально

| Проверка | Команда | Обязательно |
| --- | --- | --- |
| JVM-тесты всех модулей | `./gradlew testDebugUnitTest :engine:test` (после появления `:analysis` - и его `test`) | Всегда |
| Сборка | `./gradlew assembleDebug assembleDebugAndroidTest assembleRelease` | Всегда |
| Lint | `./gradlew lintDebug lintRelease` | При изменении Android-кода |
| Проверка workflow и скриптов | `actionlint`, `bash -n`, синтаксис Python | При изменении CI |
| Нативные host-тесты (с задачи 1.6) | `cc ... -fsanitize=address,undefined` в `transport-host.yml` | При изменении C, если окружение Linux |

Если в окружении агента нет эмулятора с аппаратным ускорением или Linux с правами на сетевые пространства имён, агент не подменяет эти проверки локальными суррогатами, а запускает CI (через черновой pull request или `workflow_dispatch`) и разбирает его артефакты. Отчёт агента всегда разделяет: прошло локально, прошло в CI, не проверялось.

### Что выполняет GitHub Actions

| Workflow | Когда | Что |
| --- | --- | --- |
| `android-build.yml` **[есть]** | push в `main`, pull request (кроме правок только документации), вручную | JVM, lint, APK, AVD API 34 базовый и расширенный наборы, проверка APK, артефакты для Pixel 7 |
| `transport-host.yml` **[есть]** | Вручную | Стенд целостности localhost; нативные host-тесты с санитайзерами добавляются в задаче 1.6 |
| DPI-стенд **[план]** | Вручную и для pull request, меняющих `:engine` или `:analysis` | Сетевые пространства имён, nftables, NFQUEUE, `tcpdump`; модели DPI из каталога; критерии приёмки движка; PCAP в артефакте. На размещённых GitHub раннерах Linux доступен `sudo` без пароля, этого достаточно для пространств имён и захвата |
| Матрица AVD **[план]** | По расписанию | API 29, 36, 37 (при наличии образа) |

### Реальный телефон без участия человека [план]

Телефон можно подключить к автоматизации через **самостоятельно размещённый раннер GitHub Actions** на компьютере пользователя, к которому Pixel 7 подключён по USB (или по ADB через Wi-Fi):

1. На компьютере устанавливается раннер GitHub Actions с меткой, например `pixel7`.
2. Отдельный workflow с `runs-on: [self-hosted, pixel7]` устанавливает собранный APK, запускает instrumented-тесты и сценарии через `adb`: Start/Stop, переключение Wi-Fi и мобильной сети (`adb shell svc wifi disable|enable`), длительную работу, сбор журнала и `dumpsys batterystats`.
3. Телефон работает в реальной сети оператора, поэтому этот workflow проверяет и обход DPI на реальной сети: пробы, диагноз и меры для заданного списка ресурсов.
4. Результаты - в артефактах того же запуска.

Безопасность: такой раннер запускается только для собственных веток репозитория и вручную (`workflow_dispatch`), никогда для pull request из форков, - иначе чужой код получил бы доступ к компьютеру и телефону. Существующий `scripts/test-pixel7.ps1` - основа для шагов этого workflow.

Облачные фермы устройств для обхода DPI не подходят: их телефоны работают не в сети пользователя.

## Реальное устройство

Пошаговый план для Pixel 7 - [PIXEL7_TESTING_RU.md](PIXEL7_TESTING_RU.md). Перед каждым этапом [ROADMAP.md](ROADMAP.md) указывает, какие сценарии повторяются. Поддержку устройства и сети не заявлять до получения результатов (п. 17 AGENTS.md).

**Привязка к артефакту.** Результат относится к конкретному APK: ссылка на запуск CI и артефакт, SHA, `versionCode`, отпечаток сертификата, API, тип подключения и режим захвата. Результат AVD или прежнего Pixel не переносится на новый APK автоматически: у нового SHA незапущенный сценарий имеет статус «не проверялось».

| Уровень | Где записывается |
| --- | --- |
| localhost (стенд целостности) | Этот документ, «Стенд целостности localhost» |
| DPI-стенд | Отчёт стенда в артефакте и строка в этом документе |
| AVD | [TRANSPORT.md](TRANSPORT.md), «Подтверждённые результаты» |
| Pixel 7 с локальной фикстурой | Отчёт `test-pixel7.ps1` и строка в [TRANSPORT.md](TRANSPORT.md) |
| Pixel 7 в реальной сети | «Серия на Pixel 7» ниже |

### Серия на Pixel 7

Задачи 2.0b и 2.5. Карточка серии заполняется до первого захода и дополняется по каждому:

| Поле | Что записать |
| --- | --- |
| Сборка | Ссылка на запуск CI, SHA, `versionCode`, отпечаток сертификата |
| Условия | Дата и время, тип сети, оператор, режим захвата, состояние зарядки |
| Цель и контроль | Ролик, время воспроизведения, точка перемотки; контрольная HTTPS-страница - выбраны до первого захода |
| Заходы | Для каждого: режим (без VPN, релей без меры, релей с мерой), начал ли ролик играть, проиграл ли заданное время, сработала ли перемотка, открылся ли контроль; причина отбраковки, если заход не засчитан (сменилась сеть, контроль недоступен) |
| Итог | 2.0b: «сбой воспроизведён напрямую», «напрямую работает» или «через релей хуже, чем напрямую». 2.5: «польза меры подтверждена», «сбой не воспроизвёлся - эффект оценить нельзя» или «мера не помогла» |

Сравнение режимов - на одном SHA в сопоставимом окне; между режимами учитывается повторное использование соединений и кэш браузера.
