# Архитектура тестовой системы

Обязательные правила задаёт [AGENTS.md](../AGENTS.md). Порядок ревью и допуска описан в [QUALITY_GATES.md](QUALITY_GATES.md). Текущие команды, состав CI и предметные критерии находятся в [TESTING.md](TESTING.md), распределение работ по этапам — в [ROADMAP.md](ROADMAP.md).

## Проектирование до реализации

До начала прикладного кода этапа свяжи требования с алгоритмическими и архитектурными инвариантами. Опиши ожидаемое и запрещённое поведение, нормальные, граничные и аварийные сценарии, тестовые данные, минимально достаточную среду, критерии успеха, ограничения и способ повтора. Для существенного сценария должен быть наблюдаемый критерий, способный отличить работающий механизм от заглушки или случайного успеха. Если средств проверки недостаточно, включи нужное развитие инфраструктуры в план и критерии приёмки этапа. Зафиксируй, требуется ли физическая проверка и почему.

## Уровни и существующая основа

Уровень выбирается по проверяемому утверждению. Один сценарий может иметь несколько реализаций на разных уровнях, если они отвечают на разные вопросы.

| Уровень | Практика проекта |
| --- | --- |
| JVM, модульные и контрактные тесты | Уже используются в `:engine` и `:vpn`. Контракты релея, отмены, диагностики, хранилища и разборщиков проверяются без Android. |
| Интеграционные тесты | Уже используются локальные TCP/UDP/TLS-фикстуры, реальные сокеты и наблюдаемые исходы. Стенд целостности localhost дополнительно проверяет сами фикстуры. |
| Модельное тестирование | Сейчас существуют отдельные модели времени и состояния. Полный подход с эталонными исходами, `ModelProbePort` и состояниями будущего анализа запланирован в TESTING. |
| Генеративное тестирование | В существующих тестах есть повторяемые случайные входы. Расширять проверку свойств по мере появления новых разборщиков и переходов. Отдельный фреймворк выбирается при доказанной необходимости. |
| Управляемый сетевой симулятор | Использовать существующие локальные фикстуры и планируемые интерфейсы транспорта проб, времени и результатов. Целостный симулятор относится к будущей аналитике. |
| Linux, native и PCAP | Есть отдельный стенд целостности и Linux-проверки операций своего сокета с захватом пакетов. Санитайзеры и стенд моделей DPI запланированы. Захват на Linux подтверждает наблюдения в этой среде. |
| Android instrumented tests | Есть проверки UI и SAF, согласия, жизненного цикла службы, TUN, HEV/JNI, диагностики, защищённого маршрута пробы и ресурсных регрессий. |
| Android AVD | Существующий CI исполняет базовый и расширенный наборы на API 34. Планируемая матрица API описана в TESTING. |
| Физические устройства | Имеются ручная инструкция Pixel 7, локальная фикстура и отдельный workflow. Реальный прогон требует допуска и разрешения пользователя. Он проверяет условия конкретного устройства и сети. |

Переиспользуй существующие механизмы. Сверяй границы доказательств в [TESTING.md](TESTING.md#уровни) и [ARCHITECTURE.md](ARCHITECTURE.md#инварианты). В частности, факт прохождения пакетов на Linux или Android AVD не устанавливает поведение DPI реальной сети.

Для самостоятельных компонентов AndroidTest APK проверяй ссылки DEX и фактическое создание компонента в его процессе до длинных тестов. Проверяй UID и PID, чтобы обращение из процесса инструментализации не скрывало зависимость от APK приложения. Для внешних сценариев с ADB добавляй хост-контроль входных сигналов, тайм-аутов и очистки. Проверяй реальный эффект отдельно на AVD. Контроли SAF и гибели VPN описаны в [TESTING.md](TESTING.md).

Если проверка зависит от порядков callback и фоновой работы, фиксируй каждый порядок отдельным сценарием. Контроль удерживает конкретный результат и ждёт завершения операции, когда это часть критерия. Переключение на `Dispatchers.IO` не гарантирует приостановку вызывающей корутины. В регрессиях SAF чтение заканчивается на диске, а выдача уже прочитанного результата удерживается до нужного события.

## Каталог сценариев

Каталог должен связывать существенные проверки и критерии, а не копировать каждый параметр тестового раннера. На текущем этапе источниками существующих Android-случаев являются списки обязательных сценариев в [базовом](../.github/scripts/verify-android-test-results.py) и [расширенном](../.github/scripts/verify-extended-transport-results.py) валидаторах. По JVM связывай требования с именованными JUnit-классами и методами. Таблица текущего этапа может использовать эти ссылки до внедрения общего формата.

Для развития выбран версионированный JSON. Его смогут читать существующие Python-проверки без новой зависимости, а JUnit и Android runner можно связать по имени класса и метода. Реализация каталога должна переиспользовать текущие списки либо генерировать их из единого источника, если такая миграция согласована. Оставляй в каталоге сведения, которых нет в исполняемых тестах и результатах. Например, время, статус и стек извлекаются из отчёта CI. Планируемый `catalog/models.json` из TESTING содержит поведение моделей, а сценарий может ссылаться на ID модели. Второе описание эталонного поведения не требуется.

| Поля | Назначение |
| --- | --- |
| `schemaVersion` | Версия формата на уровне каталога. |
| `id`, `stage`, `requirements`, `mechanism` | Устойчивый ID, этап, ссылки на требования, проверяемый механизм. ID сохраняется при переименовании метода. |
| `preconditions`, `inputs`, `events` | Предусловия, ссылки на фикстуры и последовательность событий. |
| `expected`, `forbidden`, `acceptance` | Ожидаемое и запрещённое поведение, наблюдаемый критерий успеха. |
| `environment`, `suites`, `implementation`, `limitations` | Среда, наборы, ссылки на исполняемый тест либо пометка о планировании и известные ограничения. |

Например, сценарию проверки 1.3 можно присвоить постоянный ID `S1-PROBE-TUN-01` и связать его с [тестом защищённого маршрута](../app/src/androidTest/kotlin/org/adaptivedpi/android/TunTransportInstrumentedTest.kt#L47) базового CI на API 34. Фикстура отдаёт известный ответ. Положительный контроль проходит через TUN, защищённая проба подтверждает то же содержимое без возврата в TUN. Локальная фикстура задаёт границу вывода, реальные маршруты оператора этим тестом не покрыты. Этот пример описывает формат и связывает существующий тест. Существенные сценарии этапа 1 перечислены в [машиночитаемом каталоге](stage1-test-catalog.json). Точные списки обязательных методов и результаты по-прежнему читаются из валидаторов и артефактов CI.

## Управляемая сеть и инварианты анализа

Развивай симулятор по мере появления проверяемых функциональных цепочек. Сначала переиспользуй локальные ответы, виртуальное время и интерфейсы проб. Когда для доказательства нужна реальная передача пакетов, добавляй подходящий Linux/PCAP или Android-контроль и сохраняй предел его результатов.

Сценарии симуляции должны охватывать нормальную сеть, контролируемое вмешательство, недоступность сервера, ошибки и различия DNS, региональные ограничения, сбросы, потери, задержки и нестабильность. Добавляй смену сетевых условий и физической сети, одновременную работу ресурсов, взаимодействие нескольких мер, самостоятельное восстановление, исчерпание бюджета, отмену экспериментов и перезапуск процесса. Для каждого случая известна эталонная причина, независимо заданная в фикстуре или внешнем наблюдении. Сверяй доступность ресурса, классификацию причины, выбор гипотезы и эксперимента, итоговое решение и безопасное поведение при неопределённости. Привязывай утверждения к наблюдаемому эффекту, включая ожидаемое содержимое при проверке доступности.

При реализации анализа покрывай разрешённые и запрещённые переходы, включая промежуточные состояния. Проверяй отмену, устаревание результатов, ревизию правила и эпоху сети, параллельные эксперименты, классификацию причин, достаточность доказательств, сохранение и восстановление. Отдельно контролируй лимиты времени, памяти, CPU и трафика, безопасный откат, завершение анализа и целостность обычного пользовательского трафика. Автоматический тест должен показать, что неподходящий переход не произошёл, даже если итоговое состояние выглядит правильным.

## Стенды платформы и фильтрации

Сценарии из [плана TESTING](TESTING.md#план-проверок-транспортной-платформы-и-фильтрации) проектируются до реализации каждого подэтапа. Существующие `S1-*` сохраняют идентификаторы и свидетельства. Новые существенные сценарии получают постоянный ID и запись с требованиями при появлении воспроизводимого стенда. Точные списки обязательных методов до включения новой проверки определяют действующие валидаторы.

- Для Fast Path и независимости анализа раздельно наблюдай живой трафик, транспортные операции, события датчиков, очередь анализа и сетевые пробы. Сравнивай байты приложения и семантику TCP/UDP с эталоном. Положительный контроль распознаёт исполняемую операцию. Отрицательный контроль выявляет необоснованный анализ исправного потока. В тесте отказа удерживай анализ или отдельный медленный поток управляемым событием, пока клиенты контроля получают точный ответ.
- Для многопоточных и длительных обменов используй независимые фикстуры TCP/UDP, точные payload и наблюдаемые точки запуска, отказа, смены сети, отмены и освобождения ресурсов. Сверяй удержанные и освобождённые FD, слоты, маршруты и эпохи. Повторная передача подтверждает восстановление. Заменять длительный и конкурентный прогон последовательной имитацией можно только как отдельную проверку контракта.
- Для вариантов транспорта используй неизменные входы и методы измерений, одинаковые устройство или стенд, версии, условия сети, прогрев и повторяемые окна. Отдельно измеряй простой и насыщение, задержку, пропускную способность, память, CPU, потоки, FD и энергию. Задай критерии сравнения по 1B–1C до итогового прогона. Сохраняй необработанные результаты и разброс в [архиве](TESTING.md#диагностический-архив). Локальные Linux и AVD-сценарии не заменяют физическое измерение энергии и свойств ядра устройства.
- Для фильтра используй синтетические домены, локальные DNS/CNAME-ответы и эталон разрешённых и заблокированных ресурсов. Включи общие CDN, неоднозначные UID и имена, правила наследования, конфликт исключений, PSL и нормализацию. Проверяй причину локального отказа и ноль событий анализа. Положительный контроль отдельно подтверждает доставку настоящего сетевого сбоя в анализируемую очередь.
- Для обновлений используй локальный источник, синтетический каталог реалистичного объёма и ключ исключительно стенда. Вводи сбои загрузки, проверки и атомарной публикации, конфликт доступа и перезапуск. Проверяй точную версию, активную и резервную базы, сохранность пользовательских правил, монотонность сетевой версии и отсутствие частичных решений. Интеграционная проверка охватывает Android-хранилище и совместимость APK с форматами данных.

## Сравнительные исследования транспорта и фильтрации

Программа [TRANSPORT](TRANSPORT.md#рабочие-направления-и-результаты) использует следующие серии. Начальная точка — действующий HEV и релей на принятом дереве 1A, прямой обмен с тем же изолированным сервером служит контролем. Прототипы в отдельных стендах не участвуют в рабочем тракте или Release APK.

| Серия и среда | Нагрузка, контроль и наблюдение |
| --- | --- |
| 1B-E01 · TCP/UDP/QUIC · Linux, AVD | Генератор двусторонней полезной нагрузки с фиксированным seed и хешами у получателей. Прогрев, короткие и длительные обмены, idle, FIN полусессии, RST, потери, повтор, переупорядочивание, мелкие и крупные кадры и серия с медленным peer. Сравнить прямую передачу, текущий релей и кандидаты, а для UDP отдельно менять локальное плечо. Сверить границы датаграмм, хеши, пропускную способность, время до первого байта, распределение задержек и джиттер. |
| 1B-E02 · Ресурсы, Stop и повторный Start · JVM, Linux, AVD | Синхронно поднимать контролируемое число TCP/UDP-потоков до насыщения и отпускать по барьеру. Остановить в prepare, connect, receive, write, HEV exit и дренировании с инъекцией отказа. Снимать CPU, память, потоки, FD, очереди, время освобождения и послемерный остаток. Контроли проверяют наблюдаемость неосвобождённого ресурса, своевременность разрешения Start и незатронутый соседний поток. |
| 1B-E03 · Fast Path и независимость · JVM, Linux, AVD | Сравнить без наблюдателя, с минимальной пассивной телеметрией, с ошибкой наблюдателя и с отдельной ограниченной диагностикой проблемного потока. На здоровых потоках счётчик активных и стратегических действий равен нулю. Измерить первый и последующий байты, целостность, очереди и CPU при насыщении анализа. Проверить индивидуальную область ключа, восстановление обычной передачи после снятия основания и независимость от временной остановки анализа. |
| 1B-E04 · Сети, UID и опции · host, AVD | IPv4/IPv6 и две контролируемые сети с известными DNS и endpoint, DNS64/NAT64, Private DNS, изменение MTU, прямой контроль, смена/потеря сети. Собственный socket FD, тест точного кортежа и двух приложений. Сверить API/ABI/ядро/errno с эффектом, маршруты до/после, петлю VPN, фактического получателя, отрицательные случаи v6-only и неоднозначного UID. |
| 1B-E05 · Доменный поиск и обновления · JVM, AVD | Один генератор набора, размер, fan-out, доля exact, suffix, allow и miss, смешанные имена. Оракул для правил, нормализации и конфликта, CNAME/CDN, DoH/DoT/ECH, неизвестного имени и нулевого анализа при локальном отказе. Сравнить cold/warm, cache hit/miss, параллельных читателей, latency поиска, память и время активации. Проверить неподписанный и повреждённый файл, сбой и rollback, изменения пользовательских правил, GitHub offline без влияния на транспорт. |
| 1B-E06 · Энергия и реальная сеть · отдельно разрешённое устройство | Повторить согласованные многопоточные и длительные нагрузки с одинаковым экраном, температурой, начальным зарядом, радио и сетевым состоянием. Инструментация Android и внешний замер при наличии, сохранять частоты, фактическую сеть и шум пустого прогона. AVD подходит для функциональных проверок и отдельных относительных метрик. Итоги энергии устройства требуют физической среды. |

Для серии фиксировать исходный commit/tree, build hash, версии всех компонентов/инструментов, данные среды, CPU governor при доступности, сеть, offload, нагрузку хоста, фазу прогрева, длительность, seed и параметры отказов. Порядок вариантов балансировать между повторами. Сохранять каждую попытку, исходные JSON/CSV и синтетические PCAP с метаданными, включая неуспешные. Отделять полезную скорость от скорости отправки контролем на принимающей стороне, UDP loss от задержки, задержку приложения от RTT ядра. Для CPU учитывать время процесса и всего стенда, для памяти учитывать PSS/RSS и пиковые значения, для ресурса Stop измерять от команды до фактического освобождения и стабильного повторного Start.

Пилот определяет достаточное число повторов и диапазоны рабочей нагрузки по наблюдаемому разбросу. Сравнивать медиану, хвостовые квантили, разброс и доверительные интервалы, указывать сырые значения, ожидаемые условия и ограничения обобщения. Квалификационные пороги 1C обосновываются результатами 1B, измерения 1F сопоставляются с той же исходной линией. Существующие продуктовые тесты и пороги 1A сохраняются. Первичные результаты и метрики сохраняются по [TESTING](TESTING.md#первичные-доказательства-linux-ci).

### Паспорт воспроизводимого эксперимента

Для каждой серии заполнить краткий паспорт рядом со скриптом или в отчёте. Первичные файлы и машинные метаданные имеют отдельный [формат](TESTING.md#первичные-доказательства-linux-ci).

| Поле | Содержание |
| --- | --- |
| Сценарий и контроль | ID, версия фикстуры и ревизия, запускаемая команда, выбранные положительный и отрицательный контроли. |
| Ожидаемое и запрещённое | Наблюдаемое поведение, проверка целостности, недопустимая передача или модификация, последствия сбоя и условие остановки. |
| Среда и нагрузка | Версии среды, ядро, ABI, API AVD при наличии, изоляция, параметры сети, состояние кешей и load averages, seed и состав нагрузки. |
| Метрики и пределы | Единицы, точки наблюдения, предельное время и объём файлов, бюджеты CPU/памяти/FD там, где применимо. Указать способ сверки и предел переносимости. |
| Повторяемость | Контроль начальных условий, порядок опытов и число повторов по разбросу пилота, запрет перезаписи первичного отказа. |
| Первичные материалы | Список файлов и происхождение, SHA-256, результаты положительного и отрицательных контролей, причины отсутствующих данных. |

Для инфраструктурного ревью сохранять исходную пробу, исправление и повтор на тех же данных. Проверять отдельно отказ каждого источника материалов, отказ записи сводки и сохранение доступных независимых материалов с ненулевым статусом. Состояния «проверен локально на синтетических данных», «выполнен в Linux CI» и «подтверждён физической сетью» имеют разное происхождение. [Сбор и квалификация 1B-N01](TESTING.md#первичные-доказательства-linux-ci).

## Воспроизводимость и отчёты

Для применимых сценариев фиксируй seed, начальное состояние, управляемое время и порядок событий, ответы сети и точки искусственного отказа. Записывай последовательность событий или данные, достаточные для повтора, с соблюдением правил конфиденциальности. В обязательных тестах используй локальные фикстуры и контролируемые часы там, где они достаточны. Зависимость от внешнего интернета, реальных часов или случайного порядка должна быть обоснована способом проверки.

Перед статистическим прогоном задай объём выборки, допустимую ошибку, критерии достоверности и воспроизведения. Фиксируй разброс и неопределённые результаты. Одно успешное исполнение не заменяет статистическую серию.

По возможности формируй отчёты автоматически из существующих JUnit XML, JSON валидаторов и артефактов CI. Отчёт содержит SHA, среду и версии инструментов или фикстур, выполненные и успешные сценарии, ошибки, пропуски и причины, длительность, seed или воспроизводящий вход, ссылки на диагностику, связь с требованиями. Успешным считается только действительно выполненный сценарий с подтверждённым результатом.

## Ревью тестов и реакция на дефекты

Независимый проверяющий сверяет заявленное требование с тем, что тест действительно наблюдает. Он проверяет критерий успеха, положительный и отрицательный контроль, если применимо, способность обнаружить дефект, ложноположительные исходы и необоснованные пропуски. Проверяются тестовые данные, изоляция, очистка ресурсов, воспроизводимость, соответствие поведению Android и сетевого стека. Заглушки достаточны для проверки собственных контрактов. Утверждение о реальном транспорте требует проверки на уровне, где действует этот транспорт.

Для критичных механизмов выборочно проверяй чувствительность к намеренно внесённой ошибке, включая mutation testing при технической пригодности. Эту проверку проводят на изолированной тестовой ревизии. Покрытие кода служит дополнительной метрикой. Факт прохождения теста и высокий процент покрытия сами по себе не доказывают полноту проверки.

Если дефект пропущен, выясни почему и какой класс сценариев отсутствует. По возможности добавь красную регрессию до исправления, проверь соседние случаи, при необходимости расширь общую фикстуру или инфраструктуру. Обнови каталог и включи сценарий в подходящий обязательный набор. Для системного пробела подготовь проверку всего класса, включая независимый контроль.

## Наборы и порядок запуска

| Набор | Когда нужен |
| --- | --- |
| Быстрый локальный | Во время реализации и перед передачей на ревью. |
| Обязательный регрессионный | После исправления, перед повторным ревью и на комплексной приёмке. |
| Интеграционный | Для изменённых цепочек взаимодействия, включая затронутые контракты. |
| Расширенный транспортный | При изменении общего тракта по TESTING и в соответствующей комплексной приёмке. |
| Алгоритмический | При изменении моделей, переходов, ограничений и решений анализатора. |
| Статистический | Для утверждений о вероятности, шуме и качестве классификации, по заранее заданной серии. |
| Нагрузочный и длительный | При изменении ресурсных лимитов, конкуренции, тайм-аутов или поведения под длительной нагрузкой. |
| Совместимость | При изменении Android API, ABI, поддерживаемых конфигураций или форматов данных, в рамках доступной матрицы. |
| Физическая приёмка | После допуска, если её требует этап, и только с разрешения пользователя. |

Запускай быстрые и затронутые проверки регулярно. Дорогие наборы планируй по изменениям и критериям этапа, сохраняя существующие обязательные запуски. При итоговой приёмке выполняются все обязательные для этапа наборы. Исключение выявившего дефект сценария не считается исправлением.

## Очерёдность развития

- **1A.** Переиспользовать JVM, Linux/PCAP и оба набора Android CI. Текущие результаты и системные пробелы зафиксированы в [ROADMAP.md](ROADMAP.md#доказательства-и-недостающие-проверки-этапа-1).
- **1B–1G.** Поставить одинаковые испытания возможностей и архитектур, определить критерии до реализации, добавить контроли Fast Path, фильтра, смены сети и обновления базы. На 1F выполнить длительные и нагрузочные серии. На 1G сверить совокупные доказательства и среду каждого вывода.
- **Вместе с будущим анализом.** В рамках задач 2.1–2.4 обеспечить проверку переходов с управляемыми часами, независимые сценарии эталонных причин и поступательное развитие фикстур, каталога и управляемой сети. Полнота интеграции подтверждается сквозными проверками после появления проверяемых механизмов. Источник критериев — [TESTING.md](TESTING.md#критерии-приёмки-движка-анализа).
- **Последующие этапы.** Развивать статистические серии, длительные и нагрузочные сценарии, нативные санитайзеры, матрицу совместимости и автоматизированную сводку по мере появления соответствующих требований. Каждый этап отвечает за свою инфраструктуру проверок и доказательства приёмки.

Документ задаёт направление развития. Каталог как машинный источник, полноценный симулятор, новые фреймворки и расширение CI ещё не внедрены.
