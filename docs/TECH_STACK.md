# Технологии проекта

Kotlin остаётся основным языком Android-приложения и языком адаптивного ядра. RWSE выполняется в Android-процессе и использует локальные данные. C предлагается для нативного сетевого тракта и адаптации C-компонентов. Python относится к испытательному стенду разработки. Состав каркаса этапа 1 зафиксирован в [каталоге версий Gradle](../gradle/libs.versions.toml). Технологии следующих этапов описаны для утверждения плана.

## Необходимые технологии

| Технология | Где нужна | Обоснование |
| --- | --- | --- |
| Kotlin, корутины, Jetpack Compose и Material 3 | Приложение | Android API, жизненный цикл, настройки, диагностика и стратегии реализуются в Kotlin. Compose и Material 3 образуют существующую основу русского интерфейса и единой дизайн-системы. |
| Kotlin/JVM, JUnit и виртуальное время | Общее ядро и симулятор | `:adaptive-core` хранит модели и правила принятия решений. Модуль `:adaptive-simulator` вызывает то же ядро с детерминированными событиями и тестовыми реализациями эффектов. Сами тесты используют JVM, виртуальное время и локальные фикстуры. Для запуска без SDK предусмотреть отдельную JVM-конфигурацию Gradle, если корневая сборка потребует Android SDK. [Сценарии симулятора](TESTING_STRATEGY.md#симулятор-адаптивного-алгоритма) |
| Gradle Kotlin DSL, Wrapper, AGP, JDK и Android SDK | Сборка приложения | В каркасе закреплены Gradle 8.13, AGP 8.13.2, Kotlin 2.3.21 и JDK 17. Android SDK нужен для компиляции и упаковки, а Gradle Wrapper фиксирует дистрибутив. В проекте установлен `minSdk 29`. [Каталог версий](../gradle/libs.versions.toml) · [Совместимость AGP](https://developer.android.com/build/releases/agp-8-13-0-release-notes) |
| C, JNI, Android NDK и CMake | После выбора нативного движка | Кандидаты используют C. NDK собирает выбранный компонент для Android, CMake описывает Android-цели и отдельные Linux host-цели. JNI связывает реализацию с Android-сервисом. Основная часть C тестируется из тех же исходников на Linux, а переходы JNI проверяются на Android. [NDK и CMake](https://developer.android.com/ndk/guides/cmake) · [JNI в Android](https://developer.android.com/training/articles/perf-jni) |
| JUnit и `kotlinx-coroutines-test` | Модульные тесты JVM | JUnit уже используется. Тестовые диспетчеры и `runTest` нужны при появлении асинхронных алгоритмов, чтобы воспроизводить отмену, очередь, тайм-ауты и квоты по виртуальному времени. Версию тестовой библиотеки согласуем с версией корутин приложения. [Тестирование корутин](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-test/) |
| Python и pytest | Испытательный стенд | Управляют запуском реальных компонентов с синтетической нагрузкой. Фикстуры создают и очищают стенд, параметризация проверяет варианты сценариев, результаты доступны в JUnit XML. Python и его зависимости не входят в APK. [pytest и отчёты](https://docs.pytest.org/en/stable/how-to/output.html) |
| Linux network namespaces и `tc/netem` | Полный сетевой стенд | Пространства имён ограничивают маршруты и влияние сценариев друг на друга. `netem` создаёт задержки, потери и нестабильность передачи. Точные сбои протоколов задаются тестовыми сервисами. Нужны возможности ядра и локальной настройки тестовой сети. [ip-netns](https://man7.org/linux/man-pages/man8/ip-netns.8.html) · [tc-netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html) |
| Android Emulator, ADB и Compose UI Test | Инструментальные проверки | Эмулятор и ADB обеспечивают повторяемый жизненный цикл и установку тестов. Compose UI Test проверяет видимые состояния, семантику и навигацию. Для системного согласия и части поведения фоновой службы нужен отдельный прогон Android, а итоговая совместимость проверяется на устройствах. [Тестирование Compose](https://developer.android.com/develop/ui/compose/testing) · [ADB](https://developer.android.com/tools/adb) |
| GitHub Actions | Автоматизация сборки и проверок | Существующий workflow настроен на публикацию debug APK после успешной сборки. Предлагаем добавить lint, проверки C и pytest по мере внедрения, публикацию отчётов и отдельные задания для специальной среды. [Текущий workflow](../.github/workflows/android-build.yml) · [План заданий](TESTING_STRATEGY.md#github-actions) |

## Опциональные инструменты

- **Docker** рекомендован для фиксации среды и изоляции тестовых сервисов. Первые проверки pytest с синтетическими сервисами можно запускать напрямую на Linux. Для полной сетевой матрицы Docker дополняет network namespaces и `netem`, использующие ядро Linux-host. На Windows такой стенд удобно запускать в Linux VM с проверенными возможностями ядра. [Сетевые возможности Docker](https://docs.docker.com/engine/containers/run/)
- **MockK** полезен там, где сложно воспроизвести внешний результат обычной заглушкой. Для часов, хранилища, счётчиков и последовательностей событий обычно достаточно простых управляемых реализаций контрактов. Реальные вызовы Android, маршрутизацию и JNI проверяем инструментально. [MockK](https://mockk.io/)
- **CTest и санитайзеры** полезны как способ запуска host-тестов и проверки памяти для C. CTest можно включить вместе с первыми нативными тестами. ASan и UBSan запускаем отдельной конфигурацией, когда есть нативный тракт. Производительность оцениваем по обычной сборке, поскольку санитайзеры меняют её характеристики. [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html) · [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)
- **GitHub Pages** возможен как статическая сводка обезличенных отчётов разработки. Сборка страницы и публикация отделены от APK. Установленное приложение выполняет все операции RWSE локально и работает независимо от доступности страницы. [Границы публичной сводки](TESTING_STRATEGY.md#публичная-сводка-испытаний) · [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## Нужны ли Rust или C++

| Язык | Когда имеет смысл | Стоимость для проекта |
| --- | --- | --- |
| **C** | Интеграция существующего C-компонента, небольшой JNI-адаптер или узкая переносимая часть движка с C ABI. | Требует явного управления памятью и ресурсами, тестов аварийных путей и контроля границ буферов. Один нативный набор сборки обслуживает Android и host-проверки. |
| **C++** | Выбранная зависимость имеет C++ API или собственный сложный компонент получает проверяемое упрощение владения ресурсами за счёт RAII. На стороне JNI сохраняется компактная граница с явным временем жизни. | Появляются поддержка libc++, выбор режима линковки, контроль исключений и C++ ABI, дополнительные зависимости и возможный прирост APK. Если весь выбранный транспорт на C, потребность в этой цене пока не подтверждена. [Поддержка C++ в Android NDK](https://developer.android.com/ndk/guides/cpp-support) |
| **Rust** | Появляется существенный новый модуль, который обрабатывает недоверенные данные, и прототип показывает выигрыш от безопасного владения в его основной логике. Другой вариант — выбранный Rust-компонент решает конкретную задачу, для которой C-кандидаты не подходят. | Добавляются Cargo и rustc, кросс-сборка под Android ABI вместе с NDK, C ABI или JNI-обвязка и проверка FFI, где гарантии безопасного Rust ограничены. Потребуются отдельная диагностика сборки и измерение вклада каждой нативной библиотеки в APK. [Платформы Android в rustc](https://doc.rust-lang.org/rustc/platform-support/android.html) |

Для ближайших этапов предлагаем Kotlin и, при подтверждении кандидата, C. C++ и Rust пересматриваем по конкретному компоненту. Перед добавлением языка сравниваем прототип с решением на C при одинаковой нагрузке и условиях. Фиксируем выигрыш по безопасности, сопровождению или измеримому поведению, проверяем ABI, JNI и владение ресурсами, время чистой и повторной сборки, размер нативных библиотек и прирост APK. Достаточным основанием может стать обязательное свойство, которое C-решение не обеспечивает с сопоставимой сложностью. [Матрица испытаний](TESTING_STRATEGY.md#матрица-испытаний)

При выборе версии любого нового инструмента фиксируем поддерживаемые платформы, версию, способ установки и лицензию. Для зависимостей APK отдельно проверяем ABI, размер и поддержку страниц 16 КБ, если появляются нативные библиотеки. Тестовые зависимости учитываем в составе испытательной среды. [Условия сторонних компонентов](DEPENDENCIES_AND_LICENSES.md) · [Страницы 16 КБ на Android](https://developer.android.com/guide/practices/page-sizes)
